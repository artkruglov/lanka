# Lanka Studio: совместная работа, чат и качество презентаций

Уточнение 0.6: хранение каждого клиента отдельно, без общей базы содержимого. См. [CLIENT_PROJECTS_V06.md](CLIENT_PROJECTS_V06.md).

Дата: 5 сентября 2026. Основание: оба исходных PRD, работающий код 0.4, изменения 0.5 и последние уточнения заказчика. Это актуальное дополнение к плану, а не объявление всего P0 готовым. Исходные документы сохранены без изменений.

## 1. Решение по интерфейсу

На широком экране: агент слева, затем миниатюры, большой слайд в центре и свойства справа. Глобальная навигация в редакторе сворачивается. Агент и свойства не должны взаимно заменять друг друга. На небольшом экране панели складываются последовательно; полноценную мобильную компоновку ещё нужно принять визуально.

Человек нажимает слайд, меняет текст/данные в правой панели и сразу видит результат. Сервер сохраняет новую ревизию после паузы. Есть состояние сохранения, повтор при ошибке, отмена/возврат и скачивание несохранённых правок при конфликте. Агент готовит отдельное предложение: человек сравнивает и принимает его. Это разные действия, поэтому обязательное предложение для каждой ручной правки отменено.

В 0.5 реализованы свойства целого слайда: заголовок, надзаголовок, основной текст, композиция, показатели, данные диаграммы, изображение из материалов, источники, логика и заметки. Это не свободный редактор объектов: нет выделения отдельного текстового блока на холсте, форматирования фрагмента текста, drag/resize, полноценного crop и выбора шрифта. Исходный managed-light P0 предполагал прямую правку; полный canvas и realtime были отложены отдельно.

Постоянные области будущего интерфейса:

| Область          | Что видит пользователь                                                  | Контекст действия                                    |
| ---------------- | ----------------------------------------------------------------------- | ---------------------------------------------------- |
| Агент слева      | Переписка, активная задача, вопросы, прикреплённые замечания, результат | Выбранный слайд/вся презентация; сохранённая ревизия |
| Центр            | Слайд, сравнение до/после или карта аргумента                           | Один выбранный документ, без ухода в IDE             |
| Справа: Формат   | Текст, данные, композиция, источники, заметки                           | Ручная правка с автосохранением                      |
| Справа: Обсудить | Комментарии коллег и замечания к выделенному месту                      | Слайд, блок и версия                                 |
| Справа: Проверка | Факты, переполнения, визуальные проблемы, согласование                  | Точная версия перед выпуском                         |
| Верхняя строка   | Имя, сохранение, участники, доступ и экспорт                            | Документ и его права                                 |

Текущая левая панель содержит существующий запуск отдельного запроса и файловый обмен. Она ещё не является потоковым чатом с Codex. Перемещение панели не подменяет реализацию чата.

## 2. Пространство организации и шеринг

Презентации не становятся видимыми всем автоматически. Предлагаемые режимы: «Личная», «Команде» и «Выбранным участникам». Организация может задать свой default для новых документов; изменение default не раскрывает старые документы задним числом. «Все доступные» означает объединение разрешённых документов, а не полный каталог организации.

В 0.5 есть «Мои», «Открыли мне доступ», существующие email-права owner/editor/reviewer/viewer и внутренняя ссылка. Ссылка сама право не выдаёт. Вход в приложение регулируется отдельно: текущий опубликованный Site остаётся приватным для владельца. Письма, приглашения и общая организация не реализованы; изменение доступа к документу само не добавляет человека в аудиторию приложения.

Целевая модель:

| Сущность                    | Назначение и обязательное правило                                               |
| --------------------------- | ------------------------------------------------------------------------------- |
| Organization / Membership   | Организация, действующий сотрудник, роль; все запросы ограничены organizationId |
| Workspace / Group           | Проект или команда; членство и наследование доступа явно видны                  |
| Deck / DeckGrant            | private/workspace/restricted, владелец, права участника или группы              |
| AgentPrincipal / Credential | Отдельная служебная личность, организация, разрешённые действия и срок          |
| Revision / Proposal         | Неизменяемая основа документа и ветка предлагаемых изменений                    |
| Asset / SourceSnapshot      | Объект в хранилище с hash; доступ проверяется через документ/библиотеку         |
| Conversation / Message      | История команды и агента с собственной видимостью и привязкой к документу       |
| Comment / Feedback          | Замечание, его автор, anchor, состояние и связанные исправления                 |
| Release / ArtifactManifest  | Утверждённая версия, экспортные файлы и точные зависимости                      |

Права проверяет сервер при списке, поиске, открытии документа, чтении файлов, каждом инструменте агента и скачивании выпуска. Неизвестный ID и отозванный доступ не обходятся через URL. Отзыв останавливает новые чтения и блокирует поздние записи исполняемой задачи. Уже скачанный файл отозвать технически нельзя.

Начальные человеческие роли: viewer — читать; commenter — обсуждать; editor — редактировать; reviewer — согласовывать; publisher — выпускать; owner — управлять доступом. Роли commenter/publisher и разделение автора/финального согласующего ещё нужно добавить. Администратор управляет членством и политиками; доступ администратора к содержимому должен быть отдельным явно аудируемым правилом.

У агентов та же модель разрешённых объектов, но другая личность. Вызов выполняется от AgentPrincipal с пересечением прав организации, конкретного документа и делегированного пользователем действия. Агент не получает права приглашать сотрудников, утверждать или публиковать по тому, что его запустил владелец. Передача задачи другому агенту не переносит секреты первого: новый запуск получает собственный ограниченный контекст и ссылку на результаты.

Не весь чат обязательно общий. При начале разговора выбирается «Личный с агентом» или «Обсуждение презентации». Общими становятся принятые изменения и их происхождение; личные исходные сообщения не раскрываются автоматически. Файлы личного чата нельзя незаметно использовать в доступном коллегам выпуске без решения о переносе их в материалы документа.

## 3. Прямой чат приложения с Codex — можно

Целевой путь: пользователь пишет в Lanka → API сохраняет сообщение → очередь запускает/возобновляет исполнителя → адаптер Codex App Server отправляет turn → события и результат сохраняются → браузер получает поток. Для другого агента меняется адаптер, а документ, права, переписка и review остаются теми же.

Это новая сессия исполнителя, подключённого к продукту. Она не означает автоматического доступа к текущему разговору в ChatGPT, переноса его подписки или возможности пересылать сообщения в произвольное окно Codex. Нужен поддерживаемый runtime/API и разрешённая для организации аутентификация. В репозитории уже установлен Codex и есть узкий адаптер App Server; модель и внешний worker ещё не подключены.

MCP предоставляет инструменты и ресурсы презентации. Сам по себе он не является транспортом произвольной переписки с чужим UI. Для встроенного Codex используем App Server; внешний совместимый клиент подключается к MCP и видит доступные ему документы. В будущем можно добавить отдельный протокол удалённого исполнителя с теми же контрактами.

Предлагаемые контракты следующей реализации:

- `POST /api/conversations`: создать разговор с visibility, deckId и допустимым executorProfileId.
- `POST /api/conversations/:id/messages`: clientMessageId, текст, selection, baseRevision, разрешённые attachmentIds; запись сообщения и задания атомарны.
- `GET /api/conversations/:id/events`: SSE с последовательным eventId, поддержкой Last-Event-ID; при утраченном курсоре — восстановление из снимка.
- `POST /api/runs/:id/cancel`: идемпотентная отмена, запрет поздней записи; поток показывает подтверждённое состояние.
- Адаптер исполнителя: start/resume/interrupt, capability discovery, нормализованные события и предложение результата. Провайдерские threadId/turnId хранятся внутри адаптера, не в DeckDocument.

Пользователь видит собственные сообщения, публичный ответ агента, стадии, использованные источники, выполненные действия и ошибки. Не нужно показывать или сохранять скрытые рассуждения модели как продуктовый артефакт. Смысловой план — явный результат работы: тезисы, доказательства, пробелы и переходы, который можно обсуждать и редактировать.

Доставка должна выдерживать закрытие вкладки и повтор запроса. Стабильный clientMessageId не создаёт второй запуск; последовательность событий живёт на сервере; disconnect браузера не убивает job. После падения runtime продолжение thread разрешается только при подтверждённом соответствии сохранённому checkpoint, иначе создаётся новая попытка с явным контекстом и журналом.

### Параллельная правка

Человек работает с main и автосохранением. Агент берёт сохранённую baseRevision и пишет candidate/proposal. Пока человек печатает, ответ на предыдущий save не заменяет более новый локальный текст. При конфликте main агентская правка не перетирает пользователя: независимые группы можно перебазировать, зависимые требуют решения. В 0.5 есть отклонение устаревшей записи; автоматического merge/rebase групп ещё нет. Одновременное посимвольное редактирование двумя людьми тоже не реализовано.

## 4. Браузерная и визуальная обратная связь

Агент должен видеть то же изображение слайда, что и пользователь. Для этого нужен авторитетный render service, а не только текст AST или случайный снимок браузера пользователя.

`RenderArtifact` закрепляет documentRevision/candidateId, brandPackReleaseId, версии renderer и шрифтов, hashes ассетов, viewport, PNG/PDF и manifest. Источник, шаблон и отрисовка не должны изменяться во время проверки. Кэш изолирован по организации и разрешениям; ссылки на закрытые картинки краткоживущие.

Предлагаемые MCP-инструменты: `get_slide_preview`, `get_layout_report`, `list_feedback`, `submit_feedback_response`, `submit_proposal`. Инструмент preview возвращает снимок конкретной ревизии, а не текущей страницы с куками человека. Браузерный worker с закреплённой версией Playwright открывает контролируемый preview route и может проверять переполнения и видимый результат. Сеть, пути файлов и время выполнения ограничены политикой задания. Текущий Codex worker имеет browser/shell tools отключёнными; их подключение требует отдельного ограниченного сервиса, а не снятия всех запретов.

Ручное замечание содержит `deckId`, `slideId`, `blockId?`, `baseRevision`, `renderHash?`, `region?`, текст, автора и время. Stable block ID позволяет пережить смену композиции; область изображения — дополнительный якорь, а не единственная привязка. Устаревшее замечание остаётся видимым с исходной версией. Принятие исправления связывает комментарий с proposal; агент предлагает закрытие, человек подтверждает.

Пользователь видит слайд постоянно: выделяет место → пишет замечание справа → «Передать агенту» добавляет карточку в левый чат → получает вариант → сравнивает с исходным. Правки человека сохраняются обычным способом. Агент меняет документ через проверяемые команды, а не кликает в DOM редактора от имени владельца.

## 5. Голосовая обратная связь

Сценарий: явное нажатие «Записать замечание» на выбранном слайде → запись со стопом и таймером → распознавание → редактируемая расшифровка → «Отправить агенту». До отправки это черновик, а не команда агенту. Без разрешения на микрофон остаётся текстовый ввод.

AudioFeedback хранит объект аудио в R2, mime/размер/длительность/hash, выбранный слайд и ревизию, распознанный текст, исправленный текст, автора и политику удаления. STT — отдельный утверждённый провайдер/локальный сервис с собственным таймаутом и лимитами; модель для презентаций не подразумевает поддержку аудио. Предлагаемый начальный продуктовый лимит — 2 минуты на заметку; окончательный лимит закрепляется в конфигурации и на сервере, не только в UI.

После проверки человеком расшифровка становится обычным Feedback/Message, доступным встроенному агенту или внешнему Codex через `list_feedback`. Отдельная «пересылка в IDE» не нужна. Аудио доступно только разрешённым участникам, с явным сроком хранения. Неуспешная транскрибация сохраняет черновик и позволяет повторить/ввести текст. Голосовые заметки — новое уточнение заказчика; это не найденное ранее реализованное требование. Сейчас записи и STT в коде нет.

## 6. Как поднять качество презентаций

Нужны три раздельные проверки: логика сообщения, точность данных и визуальная композиция. Один ответ модели «всё хорошо» не закрывает ни одну из них.

1. **Референс и бренд.** Для первого реального внедрения дизайнер разбирает предоставленные компанией эталонные презентации, шрифты, палитру, сетку и правила изображений. BrandPack имеет владельца, доказательства происхождения и неизменяемый выпуск. Автоматическое извлечение создаёт кандидата; сертифицирует человек.
2. **Композиции с контрактом.** Сначала довести 8–12 реально нужных типов до высокого качества: тезис, сравнение, KPI, динамика, аргумент с доказательством, решение, процесс, план, изображение. Каждый recipe задаёт обязательные смысловые поля, допустимую плотность, контентные границы и варианты композиции. Количество recipes не заменяет качество.
3. **Логика перед вёрсткой.** Бриф → аудитория и решение → план тезисов → связь claim/evidence → пробелы → слайды. Агент не выдумывает цифры для красивого макета. Человек принимает план до полной композиции; этот каркас задач уже есть, но ещё не принят на живой модели.
4. **Проверка после render.** Детерминированно проверяются границы, переполнения, контраст, минимальная типографика, единицы/даты и наличие источников. Визуальный критик получает изображения и формирует конкретные замечания со slideId. Смысловой критик отдельно проверяет тезис/доказательство/вывод. Исправления ограничены числом итераций и не меняют защищённые данные.
5. **Принять реальный результат.** Корпус коротких и длинных русских текстов, отрицательных/нулевых чисел, крупных единиц, таблиц, диаграмм, отсутствующих данных и широких/вертикальных изображений. Дизайнер сравнивает с корпоративным референсом. Экспорт проверяется отдельно: PDF-пиксели и редактируемый PPTX имеют разные ограничения.

В 0.5 визуальный стиль приложения сохранён; новые высококачественные BrandPacks не созданы. Девять прежних композиций и две палитры остаются базой пилота. Не следует выдавать улучшенную правую панель за улучшение качества готовой презентации.

## 8. Порядок следующей реализации и критерии приёмки

| Этап                                  | Конкретный результат                                                               | Проверка завершения                                                                                                               |
| ------------------------------------- | ---------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------- |
| 0.5 — текущая поставка                | Правые свойства, autosave/undo, агент слева, фильтры доступа; cloud config и аудит | Типизация, доменные тесты, тесты внешней аутентификации, production build; визуальная приёмка отдельно                            |
| A — реальный исполнитель и размещение | Cloudflare application + Fly Codex worker на реальных аккаунтах                    | Бриф + три файла → вопросы → принятый план → кандидат → принятие; cancel/conflict/restart; не объявлять готовым до живого прогона |
| B — команда                           | Organization/Workspace/Membership, человек/agent principal, приглашение и отзыв    | Три аккаунта: owner, colleague, outsider; права на deck/assets/tasks/search, отзыв во время run                                   |
| C — разговор и обратная связь         | Постоянный чат/SSE, контекст слайда, текстовые замечания → delta proposal          | Закрыть вкладку и восстановить поток; повтор не дублирует run; правка человека сохраняется                                        |
| D — визуальное качество               | Один реальный BrandPack, качественные recipes, render artifacts и browser feedback | Дизайнер принимает эталоны и fixture corpus; агент видит точный render; до/после привязано к ревизии                              |
| E — голос и выпуск                    | AudioFeedback/STT, reviewer/publisher, stored exports/manifest                     | Исправленная расшифровка до отправки; изоляция аудио; воспроизводимый выпуск и запрет обхода согласования                         |

Дизайн первого BrandPack стоит вести одновременно с подключением инфраструктуры: без него технически успешный run останется визуально слабым. Полный realtime, свободная геометрия и широкий PPTX round-trip остаются отдельными решениями после принятия основного сценария.

## 9. Что нужно от окружения

Подключить фактическую папку или репозиторий **higgsfield / shop reels.app** с deploy-конфигурацией, либо дать точный URL репозитория. В доступных материалах найдены старые документы статического прототипа Higgsfield, но не конфигурация работающего сервиса. Идентификаторы аккаунтов и ресурсов можно внести в `deploy/external.json`; токены вводятся только в secret manager выбранного окружения. Настройки внешнего размещения и миграции: [deploy/README.md](../deploy/README.md).
