# Enterprise Presentation Studio

## Канонический PRD и архитектурное задание v1.2

> **Назначение:** этот документ передаётся команде разработки как единый источник продуктовых и архитектурных требований. Версии v1.0 и v1.1 использовать только как историю решений. При расхождении действует v1.2.
>
> **Ключевой сдвиг:** продукт — не редактор с AI-панелью и не API для внешнего агента. Это **среда, в которой встроенный или внешний агент собирает презентацию через продуктовые скиллы, а человек управляет результатом через review, комментарии, точечные правки, approval и publish**.
>
> **Корпоративный бренд:** шаблон не создаётся вручную для каждой команды. Подсистема **Brand Onboarding** превращает брендбук, PPTX/POTX, лучшие референс-деки, шрифты и ассеты в сертифицированный, версионируемый **Brand Pack**. Агент выполняет большую часть извлечения и тестирования; человек всегда принимает решения и сертифицирует.
>
> **Канонический редактируемый формат:** типизированный `DeckDocument` в продукте.  
> **Файловая проекция для coding agents:** детерминированный YAML с обязательным round-trip.  
> **Основной опубликованный формат:** PDF + immutable manifest.  
> **PPTX:** импорт с реконструкцией и экспорт через отдельный адаптер, начиная с P1.

# 0. Как пользоваться документом

Документ одновременно является:

1. PRD — цели, роли, user stories, scope и метрики.
2. Верхнеуровневым ADR — решения, которые нельзя менять молча.
3. Engineering specification — модели данных, API, worker-пайплайны и security boundaries.
4. Спецификацией агентных скиллов и MCP/CLI-поверхности.
5. Спецификацией Brand Onboarding и Brand Pack.
6. Планом использования исследованных open-source-репозиториев.
7. Definition of Done и набором acceptance scenarios.

При противоречии действует приоритет:

1. Инварианты раздела 4.
2. Tenant isolation, права, human approval и безопасность недоверенных файлов.
3. Целостность `DeckDocument`, Brand Pack и ревизий.
4. Корректность authoritative preview/PDF.
5. P0 acceptance scenarios.
6. Удобство агента.
7. Удобство ручного редактирования.

Любое отклонение от инварианта оформляется отдельным ADR с оценкой миграции данных и угроз.

# 1. Резюме решения

## 1.1. Что строим

Presentation Studio состоит из четырёх взаимосвязанных подсистем.

### A. Детерминированное ядро

- `DeckDocument` и typed commands;
- versioned Brand Pack и Template Packages;
- managed semantic layout;
- authoritative render в изображения и PDF;
- deterministic lint;
- revisions, proposals, approvals и publication manifest;
- источники, data snapshots, assets и provenance.

### B. Поверхность для агента

- встроенный агент продукта;
- remote MCP server для Codex, Cursor, Claude Code и корпоративных runtimes;
- CLI и TypeScript SDK;
- один и тот же небольшой task-oriented tool catalog;
- продуктовые скиллы `deck-prep`, `deck-render`, `deck-visuals`, `brand-onboarding`;
- `AgentRun`, progress, cancellation, scopes и audit;
- proposal от конкретной base revision; агент не пишет напрямую в published deck.

### C. Поверхность для человека

- review-first экран деки;
- previews и slide thumbnails;
- semantic/content/data/source/visual diff;
- comments как основной канал человек → агент;
- partial accept/reject;
- managed-light правки текста, чисел, источников, recipe и crop;
- approval и publish конкретной ревизии.

Полный PowerPoint-подобный canvas не является P0.

### D. Brand Onboarding и Brand Library

- tenant-level Brand Library;
- intake брендбука, PPTX/POTX, референс-дек, логотипов, шрифтов и ассетов;
- безопасное извлечение кандидатов;
- Brand Profile, Writing Guide, Archetype Set, Reference Corpus, Asset Library;
- agent-readable guide к recipes;
- fixtures, goldens и тестовая дека;
- human-only certification;
- versioning, inheritance, deprecation и migration preview.

## 1.2. Продуктовое позиционирование

> **The enterprise presentation workspace where agents build and people approve.**

Клиент покупает не «генератор красивых слайдов», а управляемый цикл:

```text
Brand materials + company knowledge + files + data + comments
                              ↓
            Built-in or connected enterprise agent
                              ↓
              Semantic proposal in certified Brand Pack
                              ↓
          Render → deterministic lint → visual critique
                              ↓
         Human comments → partial review → approval
                              ↓
        Reproducible PDF + sources + data + manifest
```

## 1.3. Что продуктом не является

Presentation Studio не является:

- полным клоном PowerPoint;
- универсальным дизайнерским canvas;
- чатом, который возвращает картинки слайдов;
- агентом, пишущим HTML/CSS/PPTX-код;
- git-репозиторием презентаций;
- PDF-редактором;
- набором кастомных промптов под каждого клиента;
- инструментом автоматической публикации без человека;
- one-click-конвертером любого PPTX в идеальный шаблон.

## 1.4. Главный moat

Защищаемая часть продукта — не UI canvas и не конкретная LLM. Это связка:

1. **Product-wide skills**, которые улучшаются централизованно.
2. **Tenant-specific Brand Pack**, а не форки промптов.
3. **Семантический DeckDocument**, устойчивый к смене шаблона и агента.
4. **Review/proposal workflow**, в котором агент не перетирает человека.
5. **Brand Onboarding**, снижающий стоимость запуска следующего enterprise-клиента.
6. **Детерминированный publish**, связывающий deck, template, data, assets, fonts, approvals и renderer.

## 1.5. Две обязательные демонстрации P0

### Demo A — создание и review

> Автор загружает brief и три файла, выбирает аудиторию и сертифицированный Brand Pack. Встроенный агент собирает десять слайдов, подключает данные и визуалы, сам обнаруживает и исправляет не менее трёх layout-проблем, помечает недоказанные утверждения и устаревшие источники. Автор оставляет четыре комментария, агент создаёт второй proposal, автор принимает изменения частично, Publisher утверждает ревизию и получает PDF с manifest.

### Demo B — Brand Onboarding

> Интегратор загружает брендбук, PPTX/POTX, 20 референс-слайдов, логотипы и шрифты. Агент создаёт candidate Brand Pack, связывает каждое правило с источником, предлагает core recipes, прогоняет fixtures и собирает тестовую деку. Дизайнер исправляет кандидаты и вручную сертифицирует release. Новая дека успешно создаётся через `deck-prep` в этом Brand Pack.

# 2. Критический пересмотр предыдущих решений

| Ранее | Почему недостаточно | Решение v1.2 |
|---|---|---|
| «Редактор полностью работает без AI и позволяет создать деку с нуля» | Заставляет строить два продукта: PowerPoint-клон и agent-first среду | Без AI человек обязан уметь завершить, исправить, согласовать и опубликовать деку. Создание с нуля вручную не является P0-обязательством |
| Managed editor — центр P0 | Съедает срок, но слабо проверяет агентскую гипотезу | P0 — review-first + managed-light. Полный drag-and-drop editor — P1 |
| REST/typed API, MCP позже | Coding agents должны быть основным способом работы уже в пилоте | Remote MCP + CLI + встроенный агент используют одну application layer в P0 |
| Нет DSL/проекции в P0 | Coding agent естественно работает с файлами и diff | Канон остаётся JSON в продукте; детерминированная YAML-проекция с строгим round-trip обязательна в P0 |
| Template Studio как ручная дизайнерская среда | Стоимость внедрения не масштабируется | Brand Onboarding: агент извлекает, группирует, тестирует; человек корректирует и сертифицирует |
| Assisted import PPTX — P1 | Без шаблона реального клиента enterprise-пилот не проверяет продукт | Structural extraction и candidate generation — P0. Полноценная реконструкция произвольной деки — P1 |
| AI critique — P1 | Standalone deck без отдельного reader pass не решает заявленную задачу | Версионированный standalone critique входит в `deck-prep` P0 |
| Image generation — дополнение | Agent-first deck без visual planning превращается в текст в шаблоне | `deck-visuals` и image-style profile входят в P0 |
| 12–15 recipes как универсальная норма | Может искусственно ограничить сложный бренд или скрыть плохое покрытие | Это целевой диапазон core recipes, не жёсткий лимит. Решение определяется weighted coverage и exception rate |
| «Агент делает 80% Brand Onboarding» как обещание | Процент нельзя гарантировать до пилотных измерений | Это целевой outcome metric: доля принятых без ручного переписывания кандидатов и экономия дизайнерских часов |
| Reference decks равны правилам бренда | Лучшие деки могут быть устаревшими, исключительными или нарушать брендбук | Каждый материал получает authority/status: normative, recommended, illustrative, exception, obsolete |
| Dynamic inheritance Brand Pack | Может сделать повторный render зависимым от текущего родителя | На certification формируется immutable effective release; deck pin-ит точную версию |
| Vision-проверка блокирует publish сама по себе | Нестабильность модели создаёт недетерминированные блокировки | Deterministic lint является авторитетным. Vision critique — versioned advisory/rework signal; human review решает неоднозначность |

## 2.1. Самая опасная ошибка

Нельзя иметь два источника истины:

- JSON в базе;
- YAML-файл агента;
- текст в UI;
- HTML/SVG;
- копию внутри proposal;
- импортированный PPTX.

Правило:

> `DeckDocument` AST — единственный канон. YAML — полностью обратимая проекция AST. Layout, HTML/SVG, PDF, PPTX и screenshots — производные.

То же правило действует для бренда:

> Сертифицированный `BrandPackRelease` — immutable manifest, ссылающийся на точные версии профиля, writing guide, archetypes, templates, assets и policies. Onboarding candidates не являются runtime-истиной.

# 3. Пользователи, роли и организационная модель

## 3.1. Первичный сегмент

- компании от 200 сотрудников;
- холдинги с централизованным брендом и суббрендами;
- стратегии, finance, board office, analytics, product, presales и B2B sales;
- организации, где презентации проходят review и имеют требования к источникам, конфиденциальности и визуальному стандарту.

## 3.2. Иерархия хранения

```text
Tenant
 ├── Brand Library
 │    ├── Brand Packs / Brand Profiles / Template Packages
 │    ├── Writing Guides / Archetype Sets
 │    ├── Reference Corpora
 │    ├── Corporate Assets / Logos / Fonts
 │    └── Certification and migration history
 ├── Workspaces
 │    ├── Decks and proposals
 │    ├── Workspace assets
 │    ├── Data snapshots and sources
 │    ├── Comments and reviews
 │    └── Agent apps and runs
 └── Tenant policies / identities / audit
```

Шаблон и Brand Pack принадлежат tenant-level Brand Library. Workspace подписывается на разрешённые releases. Deck всегда фиксирует exact release.

## 3.3. Роли

### Implementation Specialist

Сотрудник нашей команды внедрения. В первом пилоте управляет Brand Onboarding вместе с клиентским дизайнером, настраивает импорт, устраняет пробелы и помогает пройти certification.

### Brand Admin

Клиентская роль после пилота. Управляет Brand Library, запускает новые onboarding runs, обновляет Brand Pack и инициирует rebrand migration.

### Brand Designer

Проверяет токены, image style, recipes, fixtures и goldens. Единственная продуктовая роль, которая вместе с уполномоченным Brand Admin может сертифицировать Brand Pack. Агент не сертифицирует.

### Author

Даёт brief и материалы, запускает агента, просматривает proposal, оставляет комментарии и выполняет managed-light правки.

### Reviewer / Commenter

Оставляет привязанные к блокам комментарии, запрашивает изменения, принимает участие в review. Может назначить комментарий человеку или агенту.

### Publisher

Утверждает конкретную ревизию и публикует PDF. Не обязан быть автором.

### Workspace Admin

Управляет членством, доступом к deck, агентными подключениями, workspace policies и подписками на Brand Packs.

### Tenant Admin / Security Admin

Управляет моделями и провайдерами, data egress, retention, scopes, service principals, классификацией и аудитом.

### Agent / Agent App

First-class non-human actor. Имеет `agentAppId`, `runId`, delegated user или service principal, scopes, skill version и audit trail. По умолчанию создаёт proposal и физически не может сертифицировать Brand Pack, approve revision или publish artifact.

# 4. Неприкосновенные инварианты

Изменение любого инварианта требует ADR и одобрения Product Lead + Tech Lead + Security Owner, если затронута безопасность.

## INV-01. Agent-first, human-final

Агент является основным способом создания и крупной переработки. Человек управляет brief, review, comments, точечными исправлениями, approval и publish.

## INV-02. Человек не зависит от AI для завершения

При недоступности модели пользователь может открыть существующий draft, исправить текст/данные/recipe/source/crop, обработать issues, согласовать и опубликовать. Обязательство создать сложную деку с нуля вручную в P0 отсутствует.

## INV-03. Один канонический DeckDocument

Все изменения человека и агента применяются typed commands к одному AST. HTML, SVG, images, PDF и PPTX — производные.

## INV-04. YAML — проекция, а не второй канон

`toYaml(fromYaml(toYaml(ast)))` обязан быть семантически эквивалентен AST. Прямой commit YAML в storage запрещён; запись проходит schema validation и command API.

## INV-05. Агент всегда работает через proposal

Агент не изменяет approved/published revision и не перетирает concurrent human edits. Proposal имеет base revision, semantic diff и rebase/conflict state.

## INV-06. Agent tools не публикуют

В tool catalog отсутствует `publish`. Publish выполняется только Publication Service после human approval и policy checks.

## INV-07. Семантика важнее координат

Агент оперирует blocks, roles, recipes, slots, sources, data и visual intents. Абсолютная геометрия не входит в обычный agent/human API.

## INV-08. Brand Pack отделён от содержания

Brand Pack управляет визуальным и языковым контрактом, но не меняет факты, источники и пользовательский смысл молча.

## INV-09. Human-only brand certification

Agent может создать и исправлять candidate, но статус `certified` выставляет уполномоченный человек. Это право не делегируется agent identity.

## INV-10. Каждое извлечённое brand-правило имеет evidence

Token, writing rule, recipe, image-style restriction и archetype candidate должны ссылаться на конкретную страницу, слайд или объект источника, иметь authority и confidence.

## INV-11. Product-wide skills, tenant-specific data

`deck-prep`, `deck-render`, `deck-visuals`, `brand-onboarding` версионируются централизованно. Клиентская специфика живёт в Brand Pack и policies. Форки скиллов под клиентов запрещены без отдельного platform ADR.

## INV-12. Effective Brand Pack фиксируется

Inheritance холдинга разрешается при compilation/certification. Runtime и published deck используют immutable effective release; изменение родителя не меняет старые deck.

## INV-13. Preview и PDF используют один render core

Authoritative preview, thumbnails и PDF получают один LayoutResult/RenderPlan. Разные layout engines запрещены.

## INV-14. Никакого произвольного tenant code

Template/Brand Pack не исполняют JavaScript, iframe, network calls, arbitrary CSS/HTML или макросы.

## INV-15. Недоверенные файлы изолированы

PPTX/POTX/PDF/SVG/fonts/images обрабатываются в sandboxed importer/asset pipeline с лимитами, malware scanning, macro stripping и без внешней сети.

## INV-16. Vision не является единственным авторитетом

Model-based visual/reader critique хранит версию модели и результат, но не заменяет deterministic lint и human approval.

## INV-17. Публикация относится к exact revision и exact Brand Pack

Manifest фиксирует deck revision, effective Brand Pack release, renderer, fonts, assets, snapshots, approvals и hashes.

## INV-18. Tenant isolation с первого коммита

Каждый row, blob, cache key, job, vector/FTS index entry, audit event и agent run привязан к tenant.

## INV-19. Ошибка явна

Система не должна молча уменьшать шрифт ниже policy, подменять font, обрезать текст, терять source, менять snapshot, flatten-ить PPTX-объект или использовать неизвестную лицензию.

## INV-20. Внешние форматы не определяют модель

PPTX/PDF/Figma/Penpot являются input/output adapters. Импорт создаёт реконструкцию с confidence/report, а не обещание round-trip.

# 5. Scope

## 5.1. P0 — первый enterprise pilot

### Core

- tenant-aware workspace и Brand Library;
- `DeckDocument`, typed commands, migrations и revision log;
- deterministic YAML projection с round-trip tests;
- 10–12 P0 block kinds, включая `steps`, `flow`, `comparison`;
- 12–18 core recipes в reference Brand Pack и 8–15 в клиентском pack по реальной необходимости;
- layout/render/lint pipeline;
- authoritative slide images и PDF + manifest;
- data snapshots, sources, charts и tables;
- asset/font registry и provenance.

### Agent-first surface

- встроенный агент продукта;
- remote MCP server и reference CLI;
- один TypeScript SDK;
- skills `deck-prep`, `deck-render`, `deck-visuals`, `brand-onboarding`;
- small task-oriented tool catalog;
- AgentRun, progress, cancellation, retries и audit;
- proposals, semantic diff, thumbnails before/after, partial acceptance;
- comments-as-input и `@agent`/assign-to-agent;
- standalone reader critique;
- eval harness по корпусу brief → proposal → review.

### Human surface

- review-first deck screen;
- inline edit текста/списков/метрик;
- source и snapshot binding;
- enable/disable block;
- reorder block/slide;
- compatible recipe switch;
- chart type switch;
- image candidate selection и crop/focal point;
- comments, review, approval, publish;
- internal tenant sharing.

### Brand Onboarding

- onboarding run в админке, ориентированный на Implementation Specialist;
- upload/classification materials;
- sandboxed PPTX/POTX/PDF extraction;
- candidates с evidence/authority/confidence;
- Brand Profile, Writing Guide, Archetype Set и image-style candidate;
- reference slide clustering и recipe candidate generation;
- agent guide к каждому recipe;
- adversarial fixture runner и golden approval;
- test deck;
- human certification и Brand Pack release;
- один внутренний и один реальный клиентский certified Brand Pack.

### Enterprise minimum

- roles и deck-level ACL;
- audit;
- basic OIDC или pilot identity integration;
- tenant/model/provider policies;
- classification-aware model/image routing;
- immutable published releases.

## 5.2. P1 — rollout

- полноценный managed editor с drag/drop slots и richer inspector;
- self-service Brand Onboarding для Brand Admin;
- расширенный Template Studio UI;
- reconstruction import существующих PPTX с confidence/report;
- native PPTX export + capability report/selective flattening;
- scheduled monthly/quarterly updates;
- one deck → multiple audience variants;
- realtime collaboration выбранных полей;
- advanced proposal rebase/merge;
- SAML/OIDC enterprise, SCIM, ABAC;
- external guests and controlled public links;
- data connectors;
- signed Brand Packs and migration automation;
- multiple image/model providers;
- private cloud/on-prem;
- tagged PDF/accessibility expansion.

## 5.3. P2

- formal StoryGraph;
- advanced multi-agent orchestration;
- full PPTX round-trip for supported subset;
- air-gapped generation;
- Figma/Penpot plugins;
- mobile/story/document projections;
- animations;
- direct vector PDF backend;
- customer-authored signed extensions;
- marketplace certified Brand Packs.

## 5.4. Non-goals P0

- pixel-perfect freeform canvas;
- arbitrary x/y authoring;
- universal PPTX compatibility;
- public template marketplace;
- customer JavaScript/plugins;
- autonomous approval/publish;
- custom prompt fork per client;
- dynamic inheritance at render time;
- model-based blocking without deterministic or human confirmation;
- full realtime CRDT document;
- storing decks in git as primary data store.

# 6. End-to-end user stories

## US-01. Создание из brief

Author: «Собери board update за Q3 из этих трёх файлов в ACME Executive. Аудитория — совет директоров, читают без докладчика».

Flow:

1. `deck-prep` проверяет brief и задаёт максимум 1–2 действительно блокирующих вопроса.
2. Загружает effective Brand Context и выбирает `board-update` archetype.
3. Извлекает утверждения, числа, источники и неопределённости.
4. Создаёт draft, вызывает `deck-visuals` и `deck-render`.
5. Исправляет deterministic issues по fallback chain.
6. Выполняет standalone reader critique.
7. Отдаёт proposal, thumbnails и summary: что сделано, что не доказано, какие данные stale.

**Acceptance:** при передаче человеку нет blocking deterministic issues; каждое ключевое число имеет source/date или явную unresolved issue.

## US-02. Comments → agent

1. Reviewer оставляет комментарии на стабильных block IDs.
2. Назначает thread встроенному или подключённому агенту.
3. Agent читает comments, создаёт новый proposal от указанной base revision.
4. Review UI показывает semantic diff и before/after.
5. Author принимает отдельные change groups.
6. Thread закрывается только после принятия соответствующего изменения человеком.

## US-03. Managed-light правка без агента

Author исправляет опечатку, метрику, source, recipe, chart type или crop. Изменение идёт тем же command API, создаёт human revision и остаётся видимым агенту. BaseRevision предотвращает перезапись.

## US-04. Standalone reader pass

Для `deliveryMode=standalone` агент читает deck как незнакомый участник целевой аудитории и проверяет:

- заголовок является выводом;
- есть контекст и so-what;
- сокращения расшифрованы;
- доказательство связано с утверждением;
- отсутствуют критические сведения только в notes;
- последовательность понятна без голоса автора.

Результат — versioned critique issues. Они исправляются proposal-операциями или явно принимаются reviewer-ом.

## US-05. Данные

Agent или Author загружает CSV/JSON snapshot, привязывает chart/table/metric. Lint проверяет schema, units, period и freshness. Publish фиксирует snapshot hash и as-of date.

## US-06. Review и publication

Author отправляет exact revision. Reviewer комментирует. Publisher approve-ит revision. Только после этого Publication Service создаёт PDF и manifest. Agent не имеет publish tool/scope.

## US-07. Регулярный отчёт

P0 модель обязана поддерживать связь с previous published release и immutable snapshots. UI automation — P1.

P1 flow:

1. Agent берёт прошлую опубликованную revision и новый snapshot.
2. Создаёт proposal.
3. Diff показывает не только текст, но KPI/data/source/narrative changes.
4. Неизменившиеся утверждения не переписываются стилистически без причины.

## US-08. Одна дека — разные аудитории

P0 модель хранит content blocks и sources независимо от presentation view. P1 agent создаёт новую audience variant с другим archetype, глубиной и ordering, сохраняя lineage.

## US-09. Brand Onboarding

1. Implementation Specialist создаёт onboarding run.
2. Загружает обязательные и рекомендованные материалы.
3. Agent классифицирует, извлекает и показывает кандидаты с evidence.
4. Brand Designer правит/принимает Brand Profile, Writing Guide и image style.
5. Agent группирует curated reference slides в recipe families.
6. Designer подтверждает semantic slots и exceptions.
7. Fixture runner выполняет adversarial suite; agent исправляет candidate в допустимых пределах.
8. Agent собирает test deck по реальному brief.
9. Designer и target authors оценивают rubric.
10. Human certifier публикует immutable Brand Pack release.

## US-10. Tenant Admin

Устанавливает:

- допустимые text/image models и regions;
- правила data egress по classification;
- agent scopes и quotas;
- retention raw onboarding files;
- rights policies для fonts/assets;
- audit export;
- кто имеет право certifying/publishing.

## US-11. Визуалы

На каждый слайд `deck-visuals` выбирает приоритет:

1. Corporate Brand Library.
2. Data-driven chart/table.
3. Structural visual (`steps`, `flow`, `comparison`, `timeline`).
4. Approved stock/generation provider.

Generated asset создаётся как candidate с provenance и не попадает в approved revision без принятия.

## US-12. Миграция бренда

Brand Admin создаёт новую major release. Система компилирует effective pack, прогоняет corpus/fixtures и строит migration preview для deck. Старые published artifacts остаются привязаны к прежней release.

## 9.4. YAML projection

Проекция предназначена для coding agents и human-readable diff.

```yaml
deck:
  title: Q3 Board Update
  audience: board
  delivery: standalone
  archetype: board-update
  brand_pack: acme.core@3.2.1

slides:
  - id: retention
    role: insight
    message: "Retention, not acquisition, limits growth"
    recipe: evidence-split
    blocks:
      - metric:
          id: m3-retention
          value: -18%
          label: M3 retention
          source: dwh-retention-q3
      - chart:
          id: cohort-chart
          binding: retention-snapshot
          intent: trend
```

Правила:

- formatter имеет canonical ordering;
- unknown fields отклоняются либо сохраняются только через versioned extension registry;
- IDs не регенерируются при форматировании;
- parser возвращает semantic command plan/diff, а не пишет AST напрямую;
- stale base revision требует rebase;
- comments/review state в YAML не редактируются произвольно.

## 10.3. Recipe contract

```yaml
id: insight-evidence-split
version: 3

whenToUse:
  - one dominant claim
  - one chart, table, or image as primary proof
avoidWhen:
  - more than two unrelated claims
  - table wider than eight columns

accepts:
  slideRoles: [insight, evidence]
  requiredRoles: [headline, claim, evidence]

slots:
  title:
    accepts: [headline]
    maxLines: 2
  statement:
    accepts: [claim, metric]
    cardinality: [1, 2]
  evidence:
    accepts: [chart, table, image, flow, comparison]
    cardinality: [1, 1]

constraints:
  minFontSize: 22
  maxTitleLines: 2
  allowOverflow: false

fallback:
  - insight-stack
  - evidence-full-width
  - split-slide

examples:
  good: [ref-slide-183, ref-slide-221]
  bad: [fixture-overloaded-claim]
```

## 10.4. Agent guide

Compiler contract недостаточен модели. Для каждого recipe хранится:

- когда применять;
- когда не применять;
- обязательные смысловые роли;
- допустимое количество blocks;
- content budget в терминах смысла и строк, а не только символов;
- good/bad examples;
- fallback rationale;
- требования к визуалу;
- требования к source note;
- standalone guidance;
- типичные ошибки.

Agent guide генерируется/обновляется в Brand Onboarding, но сертифицируется вместе с package.

## 10.5. Image-style profile

Минимальные поля:

- allowed visual types;
- photo vs illustration policy;
- palette and contrast;
- composition and negative-space guidance;
- people/face policy;
- prohibited text/logos/brands;
- icon family;
- reference assets;
- approved provider routes;
- prompt scaffold;
- post-generation checks;
- disclosure policy.

Агент не создаёт свободный несвязанный prompt: он формирует `VisualIntent`, который компилируется через profile.

## 10.6. Versioning

### Brand Pack

- Patch — исправление без изменения contracts.
- Minor — новый совместимый recipe/archetype/asset policy.
- Major — rebrand, несовместимые token/slot/writing/archetype rules.

### Deck pinning

- Workspace может подписаться на channel (`latest-certified`, `major-3`, exact).
- Новый deck получает выбранную release policy.
- Созданный deck хранит exact release.
- Existing deck никогда не меняется молча.

### Inheritance

Parent + overrides компилируются в effective profile. Certification фиксирует результат и hash. Runtime не разрешает наследование заново.

# 11. Brand Onboarding

## 11.1. Цель

Снизить стоимость и время превращения реального корпоративного бренда в production-ready Brand Pack, не выдавая probabilistic extraction за сертифицированное правило.

Формула процесса:

> **Agent proposes and tests; designer decides and certifies.**

Цель «агент делает 80%» является метрикой эффективности, а не разрешением агенту принимать нормативные решения.

## 11.2. Кто выполняет

### Первый enterprise pilot

- Implementation Specialist нашей команды;
- Brand Designer/Brand Admin клиента;
- 1–2 target Authors для test deck;
- Security/Legal при fonts/assets/model egress.

### После пилота

Brand Admin клиента использует тот же wizard self-service. Full self-service UX может быть P1; P0 обязан хранить правильную domain model и дать рабочий implementation-led flow.

## 11.3. Входные материалы

### Обязательные

- PPTX/POTX templates, masters и layouts;
- brand book PDF;
- vector logos;
- fonts и документы о правах.

### Рекомендованные

- 10–30 curated current high-quality decks;
- tone/language guide;
- terminology/glossary/prohibited phrases;
- corporate photo/icon/illustration library;
- список archetypes и typical audiences;
- примеры «плохих» или deprecated decks для отрицательной разметки.

Важно: reference decks не принимаются как норматив автоматически. Intake требует owner, date, business unit и authority.

## 11.4. Pipeline

### Step 0. Onboarding brief

До загрузки фиксируются:

- target business units;
- primary deck archetypes;
- languages;
- delivery modes;
- aspect ratios;
- expected PDF/PPTX needs;
- confidentiality classifications;
- approved model/image providers;
- success rubric;
- current baseline времени дизайнера.

### Step 1. Intake и classification

- upload в quarantine;
- antivirus/malware scan;
- zip bomb/macro/external-link checks;
- content hash;
- material classification;
- owner/date/authority/classification;
- duplicate detection;
- retention policy.

### Step 2. Sandboxed extraction

Из PPTX/POTX:

- page geometry;
- themes, masters, layouts, placeholders;
- fonts/colors;
- recurrent objects;
- images/assets;
- thumbnails;
- object geometry for analysis only.

Из brand book:

- candidate colors/fonts/spacing/logo rules;
- image style and prohibited usage;
- wording and naming rules;
- source page mapping.

Из reference decks:

- slide embeddings/features;
- recurring composition clusters;
- likely semantic roles;
- archetype patterns;
- exceptions and outliers.

Extractor работает без внешней сети и не создаёт certified objects.

### Step 3. Source authority и conflict resolution

Порядок по умолчанию:

1. current normative brandbook/policy;
2. approved current master/template;
3. curated current exemplar decks;
4. observed repeated pattern;
5. isolated exception.

Конфликт не разрешается silently. UI показывает:

- conflicting candidates;
- sources;
- dates;
- authority;
- confidence;
- likely impact.

Human выбирает или формирует override.

### Step 4. Brand Profile

Agent предлагает:

- design tokens;
- type scale and font usage;
- page and safe-area geometry;
- logo variants/clear space/background rules;
- image-style profile;
- accessibility defaults;
- subbrand inheritance/overrides.

Designer принимает по секциям, видя evidence рядом.

### Step 5. Writing Guide и Archetypes

Agent извлекает:

- tone;
- glossary;
- naming;
- prohibited terms;
- acronym rules;
- current examples;
- deck archetypes and contracts.

Для каждого archetype создаются 2–3 curated examples и антипримеры. Reference content остаётся tenant-bound и не используется вне разрешённого context.

### Step 6. Recipe discovery

1. Curated slides классифицируются по archetype/role.
2. Agent предлагает clusters.
3. Designer объединяет/разделяет кластеры.
4. Agent строит recipe candidates из approved primitives.
5. Slots получают semantic roles.
6. Для каждого recipe формируется agent guide.
7. Uncovered slides маркируются exception/obsolete/new-recipe candidate.

### Coverage metric

Не использовать простое «покрыто N% всех слайдов». Используется weighted coverage:

```text
weighted_coverage = Σ(weight(slide) × covered(slide)) / Σ(weight(slide))
```

Вес учитывает:

- частоту archetype;
- business criticality;
- current/obsolete status;
- normative/recommended authority;
- duplicated variants.

Целевой exit criterion пилота:

- ≥80% weighted coverage core use cases;
- все critical archetypes имеют достаточное покрытие;
- core recipe count обычно ≤12–15, но может быть выше по ADR;
- exceptions явно перечислены;
- ни один high-frequency slide family не скрыт в «exception» ради метрики.

### Step 7. Fixtures и goldens

Обязательный набор включает:

- RU/EN long/short titles;
- DE long words при заявленной локализации;
- RTL/CJK, если в scope;
- 1/3/10 bullets;
- metric: negative/large/percentage/currency;
- table 3×3, 15×8 и long headers;
- chart with long labels/missing values;
- no image/portrait/landscape/low resolution;
- 0/1/3 source notes;
- confidential watermark/footer;
- missing font/fallback;
- contrast/alt text/reading order;
- multiple aspect ratios, если поддерживаются.

Agent может менять candidate recipe within schema и повторять run. Max iterations and cost are bounded. Designer approves goldens.

Renderer upgrade, изменяющий visual fingerprint выше threshold, требует compatibility run и при необходимости recertification.

### Step 8. Test deck

- Brief берётся из реального или de-identified клиента case.
- Используются production skill versions.
- `deck-prep` + `deck-visuals` + `deck-render` создают 10-slide deck.
- 1–2 target Authors и Brand Designer оценивают rubric.
- Все unresolved questions/issues сохраняются.

### Step 9. Certification

Сертификация доступна только human role и требует:

- valid schemas;
- resolved blocking conflicts;
- passed security checks;
- approved fonts/asset rights;
- fixture pass;
- approved goldens;
- test deck above threshold;
- compiled effective release hash;
- migration policy;
- signed audit event.

### Step 10. Publication и subscription

- Release публикуется в Brand Library;
- workspaces получают subscription policy;
- deck creation pins exact release;
- usage and failures feed onboarding analytics;
- candidate raw materials follow retention policy.

## 11.5. Что хранится

| Layer | Содержимое | Consumer |
|---|---|---|
| Effective Brand Profile | tokens, typography, logo, page, image style, accessibility | compiler, renderer, deck-visuals |
| Template Packages | components, recipes, policies, fixtures, agent guide | layout, lint, agents |
| Writing Guide | tone, language, glossary, prohibited wording | deck-prep, lint |
| Archetype Set | contracts, examples, anti-patterns | deck-prep, standalone critique |
| Reference Corpus | curated labeled references | onboarding, eval, controlled RAG |
| Asset Library | logos, photos, icons, illustrations, rights | deck-visuals, renderer |
| Certification | tests, goldens, rights, versions, waivers | registry, audit, publish |

## 11.6. Exit criteria пилота

Плановое ожидание для крупной компании: 2–3 календарные недели и 3–5 person-days клиентского дизайнера. Это hypothesis/SLA target, а не contractual guarantee до измерений.

Готово, когда:

- weighted reference coverage ≥ согласованного порога;
- critical archetypes covered;
- fixtures без blocking overflow/security/rights issues;
- test deck выше rubric threshold;
- source evidence присутствует у всех normative rules;
- font rights подтверждены для web/render/PDF use;
- assets имеют known rights state;
- designer hours и cycle time измерены;
- human certifier опубликовал release.

## 11.7. Метрики Brand Onboarding

- elapsed time to certified release;
- implementation hours;
- client designer hours;
- candidate acceptance rate without edit;
- candidate edit rate;
- weighted coverage;
- recipes per 80% coverage;
- exception rate;
- fixture first-pass/final pass rate;
- test deck rubric score;
- false-positive/false-negative brand lint rate;
- number of custom schema gaps;
- rebrand migration success.

## 12.3. Skill: deck-prep

7. return clean status or escalate unresolved issues.

4. use approved stock/generated asset.

- selected/candidate asset refs;
- provenance;
- alt text;
- crop/focal point;
- explicit generated/stock/corporate label.

4. proposes Brand Profile, Writing Guide, Archetypes and image style;
5. clusters reference slides;
6. proposes recipes and agent guides;
7. runs fixtures;
8. creates test deck;
9. prepares certification report.

It cannot certify.

## 12.7. Skill versioning

- Skill has semver, changelog and eval suite.

- Breaking input/output change requires major version.
- Tenant cannot fork prompt invisibly.
- Tenant-specific behavior is data in Brand Pack/policies.

## 12.8. Agent context budget

# 13. Layout, renderer, lint и critique

## 13.1. Pipeline

```text
DeckDocument + BrandPackRelease + Data/Assets
                    ↓
        Compatible recipe candidates
                    ↓
       Real font and intrinsic measurement
                    ↓
             LayoutResult/RenderPlan
                    ↓
          Slide images + deterministic lint
                    ↓
             Optional visual critique
                    ↓
          Repair commands / human escalation
                    ↓
          Authoritative preview and PDF
```

## 13.2. Hard constraints

- overlap;
- clipping;
- overflow;
- missing glyph;
- unapproved/missing font;
- below min font size;
- outside safe area;
- wrong slot cardinality;
- missing required source/footer;
- unsupported asset/license;
- security/classification violation.

## 13.3. Fallback order

1. remove/shorten optional annotation when policy permits;
2. choose compact component variant;
3. alter split ratio within recipe limits;
4. choose alternate compatible recipe;
5. move detail to appendix;
6. split block/slide;
7. modest font change within approved range;
8. return unresolved issue.

Agent cannot silently summarize a legal/financial statement merely to fit; content-changing fallback creates explicit diff.

## 13.4. Vision/reader critique

Structured output only:

- issue kind;
- slide/block refs;
- severity suggestion;
- confidence;
- concise observable rationale;
- suggested semantic remedy.

No private chain-of-thought is stored or shown. Prompt/model/version are handled by privacy policy; hash and route metadata are retained.

## 13.5. Authoritative rendering

P0:

- DOM/SVG painter;
- pinned Chromium/Playwright image;
- approved fonts bundled/mounted;
- no external network;
- isolated worker;
- page screenshots and PDF from same render job;
- content-addressed render cache.

Byte-identical PDF is not required in P0; page visual fingerprints and input manifest must be stable within threshold.

- sanitization;

- provenance;
- deletion/retention policy.

Uploaded text is data, not instruction. Skills must not obey instructions embedded in client documents unless explicitly part of a trusted policy source.

## 16.2. Model/provider governance

- allowed provider/model/region by classification;
- no training/data retention contractual flags;
- tenant-managed keys where required;
- redaction/minimization;
- external agent access can be narrower than built-in agent;
- brand normative materials may be inaccessible to third-party agents unless approved;
- prompt/raw content not placed in general logs.

## 16.3. Certification separation of duties

- Candidate author/agent may not certify.
- Optional two-person certification for high-risk tenant.
- Rights waivers require named human approver.
- Certification event immutable and auditable.

## 16.4. Supply chain

- pinned dependencies and container digests;
- SBOM;
- license inventory;
- signature verification where available;
- isolated OSS adapters;
- no AGPL code in proprietary core without commercial agreement and legal approval.

# 26. Acceptance scenarios

## AC-01. Agent creates greenfield deck

Given certified Brand Pack and three source files, when Author runs `deck-prep`, then proposal contains ten rendered slides, zero blocking deterministic issues, source/date status and summary of unresolved claims.

## AC-02. Comment-driven fix

Given four comments on three blocks, when assigned to agent, then a linked run/proposal is created and reviewer can accept changes independently.

## AC-03. Human edit concurrency

Given agent proposal from revision 10 and human change at revision 11, when proposal is opened, then system rebases clean changes and flags same-field conflict without data loss.

## AC-04. YAML round-trip

Given a DeckDocument, when exported, formatted, parsed and planned, then semantic AST/IDs remain equivalent. Unknown/stale edit is rejected with structured error.

## AC-05. Agent cannot publish

Any MCP/CLI/built-in agent attempt to publish/approve/certify fails even if it crafts raw endpoint request.

## AC-06. Brand material conflict

Given old template uses color A and current brandbook requires B, onboarding shows both sources/date/authority and waits for human decision.

## AC-07. Brand evidence

Every accepted normative token/rule/recipe has at least one valid EvidenceRef. Certification blocks missing evidence unless explicit human waiver policy allows it.

## AC-08. Weighted coverage

Coverage excludes obsolete/duplicate slides according to documented weighting, displays uncovered high-frequency families, and cannot be raised by silently relabeling them as exceptions.

## AC-09. Fixture overflow

Long RU headline and 15×8 table trigger fallback or blocking issue; no hidden clipping and no font below policy.

## AC-10. Brand certification

Agent submits candidate. Only authorized human can certify. Release manifest pins exact components, renderer compatibility and test results.

## AC-11. Subbrand inheritance

Parent update does not alter existing certified child release or deck. New child release requires compilation/certification.

## AC-12. Image egress denied

Confidential slide cannot call external image provider when policy denies it. Agent receives policy-safe alternative options.

## AC-13. Asset rights

Unknown-license stock image blocks external publish; approved AI-generated asset records provider/model/request hash and disclosure status.

## AC-14. Reproducible publish

Same deck revision, Brand Pack, data, assets, fonts and renderer produce same input fingerprint and page visual fingerprints within threshold.

## AC-15. Prompt injection

Instruction embedded in uploaded brandbook to exfiltrate files is treated as document content and cannot alter tool scopes or cause network access.

## AC-16. Test deck gate

Brand Pack cannot be certified until production skills build the test deck and required human rubric results are stored.

| Risk | Impact | Mitigation |

# 31. Final instruction to the team

Do not optimise for the demo «AI drew twenty attractive slides».

Optimise for two repeatable loops:

```text
Brief/files → agent skills → proposal → render/lint → comments →
partial acceptance → approval → reproducible PDF
```

and

```text
Brand materials → agent candidates with evidence → designer decisions →
recipes/fixtures/test deck → human certification → Brand Pack release
```

The product is not ready while either loop requires hidden manual database edits, custom client prompts, hand-written HTML, silent policy exceptions or an agent with publish/certify power.

The strongest enterprise promise is:

> **A company can connect its agents, onboard its real brand once, repeatedly turn governed knowledge into on-brand presentations, review every semantic change, and publish a document whose design, data, sources, assets and approvals are all traceable.**
