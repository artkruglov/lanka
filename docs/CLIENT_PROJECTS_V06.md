# Lanka 0.6 — агент в проекте клиента

Обновление 0.7: добавлен локальный редактор той же папки с человеческим принятием proposals. Актуальные возможности и ограничения: [ARCHITECTURE_AND_DESIGN_V07.md](ARCHITECTURE_AND_DESIGN_V07.md). Ниже сохранена исходная граница 0.6.

5 сентября 2026. Последнее уточнение заказчика меняет базовую архитектуру: предпочтителен отдельный контур каждого клиента с документами в его хранилище. Общая база содержимого всех организаций и общий агент с доступом ко всем клиентам не являются целевой моделью.

## Бизнес-требования

| ID     | Требование                                                | Приёмка                                                                                              |
| ------ | --------------------------------------------------------- | ---------------------------------------------------------------------------------------------------- |
| CP-001 | Клиент контролирует папку, материалы и доступ сотрудников | Администратор клиента выбирает хранилище; файлы можно забрать без привязки к нашей модели            |
| CP-002 | Один запуск работает с одним выбранным проектом           | Другой deckId/path нельзя прочитать через это подключение; нет общего поиска клиентов                |
| CP-003 | Человек видит и редактирует слайды                        | Прямое редактирование справа; агент слева; сохранение и конфликт видимы                              |
| CP-004 | Изменения агента проходят review                          | Предложение не меняет основной документ; approve/publish отсутствуют в инструментах агента           |
| CP-005 | Папка переносима                                          | Документ, бренд, материалы, комментарии и версии читаются без собственной центральной базы           |
| CP-006 | Доступ наследуется от выбранного хранилища                | Отзыв прав блокирует следующие чтения; ссылка и импорт не создают новых разрешений                   |
| CP-007 | Имеется замкнутый агентский сценарий                      | Прочитать бриф → создать → проверить → показать → получить замечания → предложить исправление        |
| CP-008 | Работа с файлами не теряет изменения                      | Один авторитетный writer, атомарная запись и проверка ревизии; восстановление после отказа проверено |

Папка — удобная продуктовая граница, но не достаточная защита сама по себе. Для разных клиентов нужны отдельные учётные данные, область хранения, очередь/worker и разрешённый контекст. Локальный MCP ограничивает свои инструменты выбранной папкой; он не запрещает другим инструментам Codex читать файлы, к которым имеет доступ его ОС-пользователь. Для сильной изоляции worker запускается с отдельным пользователем/контейнером и только нужным mount, без глобальных ключей других клиентов.

## Что сделано в 0.6

1. В «Экспорт» добавлена **«Папка проекта»**. ZIP включает основной `project.json`, представление документа, бриф, комментарии и фактические материалы с проверкой SHA-256. Приложение не переносит в ZIP права доступа и утверждение как действующие полномочия. Лимит — 40 МБ материалов, до 5 МБ на файл.
2. Реализован отдельный **stdio MCP для одной папки**: `get_project`, `create_deck`, `propose_changes`, `add_comment`, `lint_deck`, `export_deck`. В вызовах нет произвольного пути или переключения клиента. Чужой deckId отклоняется.
3. Локальное состояние записывается через эксклюзивный lock и атомарное переименование; повторы команды имеют сохранённый requestId. Ссылки на файлы/папки через symlink отвергаются. Нет автоматического захвата оставленного lock.
4. Создана демонстрационная презентация из 7 слайдов реальными вызовами этого MCP. Получены PPTX и PDF; проверка структуры и переполнений прошла. Это вызовы из текущей задачи, **не отдельный авторизованный запуск модели Codex**.
5. Добавлены тесты протокола, изоляции проекта, повторной команды, proposals, конкурентной записи, symlink и целостности ZIP.

Веб-приложение по-прежнему сохраняет свои документы в D1/R2. ZIP — самостоятельный снимок, а не непрерывная синхронизация. Полный файловый backend веб-редактора, коннектор корпоративного диска, передача live-изменений и production isolation ещё не реализованы.

## Папка проекта

| Путь                                 | Назначение                                                                                          |
| ------------------------------------ | --------------------------------------------------------------------------------------------------- |
| `project.json`                       | Авторитетное локальное состояние: документ, ревизия, источники, комментарии, предложения и receipts |
| `presentation/deck.json`             | Переносимое представление AST для импорта в редактор; это снимок                                    |
| `brief.txt`                          | Бриф из сохранённого документа, также снимок                                                        |
| `materials/<sha256>.bin`             | Точные байты источников; имя/type/id описаны в основном состоянии                                   |
| `feedback/comments.json`             | Выгрузка обсуждения; основной журнал в project.json                                                 |
| `exports/presentation.pptx` / `.pdf` | Созданные MCP артефакты черновика; экспорт не равен публикации                                      |
| `write.lock`                         | Только во время локальной записи; не удалять, пока writer активен                                   |

Пользователь может положить ZIP в разрешённый корпоративный диск и предоставить доступ коллегам штатными средствами этого диска. Не запускать независимых writers поверх потребительской синхронизации файлов: локальный lock не является распределённой блокировкой. Для общего онлайн-редактирования нужен один project service с CAS/ETag провайдера и журналом версий.

## Подключить к локальному Codex

Из репозитория:

```sh
npm ci
npm run build:mcp
```

Распаковать экспортированную папку проекта либо создать пустую папку для новой презентации. Затем подключить **один конкретный проект**, заменив абсолютные пути на свои:

```sh
codex mcp add lanka-project -- node /ABS/LANKA/.project-runtime/server.mjs --root /ABS/CLIENT/PROJECT
```

Команда не содержит ключей облаков. Для другой папки создаётся отдельная явно выбранная конфигурация; не добавлять папки всех клиентов в один активный профиль. В production использовать изолированное окружение клиента. Аутентификация самого Codex выполняется отдельно поддерживаемым способом; наличие локального MCP не даёт доступ к модели.

Проверка и пример запроса:

```text
Работай только через lanka-project. Вызови get_project.
Если проект пуст, создай презентацию из моего брифа.
Затем проверь lint_deck и экспортируй PPTX/PDF.
Если документ уже существует, предложи изменения без применения.
Не утверждай, не публикуй и не открывай другие проекты.
```

Codex поддерживает stdio и HTTP MCP; Web/Work и локальная конфигурация — разные поверхности. [Официальная документация MCP](https://learn.chatgpt.com/docs/extend/mcp?surface=cli). Для встраивания собственного левого чата используется адаптер App Server, а не управление чужим окном браузера. [Codex App Server](https://learn.chatgpt.com/docs/app-server).

### Границы первой локальной реализации

Одна презентация на корневую папку; до 40 слайдов; до 12 открытых proposals и 300 комментариев; состояние до 1,5 МБ; входящая строка MCP до 1 МБ. До 500 изменяющих команд на локальный проект: после этого требуется контролируемое архивирование, receipts молча не удаляются. Lock и atomic rename дают сериализацию локального writer, но не доказательство корректности любого сетевого диска. Отдельного фонового автоматического merge и приложения для человеческого принятия локальных proposals пока нет. Основной документ можно импортировать через `presentation/deck.json`; материалы между инстансами требуют отдельного переноса. Синхронизация назад в веб-проект не обещана.

## Проверка страницы Codex и hosted MCP

Страница Codex была открыта в браузере; видимая форма требует входа. Подключённой авторизованной сессии там не подтверждено. Попытка запуска установленного runtime была прервана на сетевом разрешении; живой inference не подтверждён.

У опубликованной 0.5 отсутствовала декларация MCP, несмотря на существующий `/api/mcp`. Платформа явно ответила: «The published Site does not declare an MCP server». Прямой запрос с выданным платформой доступом также получил 401. Это не исправляется подстановкой заголовков личности пользователя. В 0.6 добавлен совместимый `/mcp` route, но это само по себе не регистрирует MCP на платформе. Попытку декларации `mcp.path` хостинг отклонил как неподдерживаемое поле; оно удалено из конфигурации. Hosted MCP не считается подключённым: нужны поддерживаемая регистрация на платформе, OAuth-подключение клиента и успешный живой вызов. Рабочая демонстрация 0.6 использует локальный stdio MCP.

## Что делать дальше

1. **Один реальный клиент.** Выбрать его конкретную папку и сервис хранения, подтвердить владельца и принятую политику доступа. Предпочтителен управляемый instance клиента; общий control plane хранит только параметры подключения/состояние, без материалов и глобального ключа ко всем данным.
2. **Project service.** Подключить клиентский storage adapter с версиями и CAS, сделать папку авторитетной для UI, добавить обновление отображения при изменениях и human accept локального proposal. Ветки changes/review остаются совместимыми с текущим AST.
3. **Живой Codex.** В отдельном окружении клиента подключить runtime к модели, закрепить только этот project MCP, выполнить бриф → план → слайды → замечание → delta → accept. Сохранить реальные результаты; текущая демонстрация проверяет инструменты, а не генерацию отдельной моделью.
4. **Шаблон и обратная связь.** Первый настоящий BrandPack, изображения точных ревизий для агента, чат/SSE, затем голосовые замечания. Не откладывать качество слайдов за счёт расширения централизованной инфраструктуры.

Это уточнение заменяет в `PRODUCT_WORKSPACE_V4.md` приоритет общей мультитенантной базы содержимого. Требования к review, источникам, качеству и воспроизводимому выпуску сохраняются.
