# Lanka v0.8 — брифинг, дизайн и цикл обратной связи

Проверено 5 сентября 2026 года. Это работающий пилот с ограничениями, а не завершённая enterprise-платформа.

## Что изменилось

| Требование | Реализация | Практический предел |
|---|---|---|
| Начать без большого контекста | Название → три вопроса → подтверждение брифа | Базовые вопросы детерминированы; дополнительные формирует подключённый агент |
| Не выдумывать ответы | Допущения отмечаются, передаются в контекст и сохраняются | MCP хранит происхождение со слов агента; не может доказать, что разговор состоялся |
| Корпоративные шаблоны | Folio для продаж, Boardroom для отчётов; 10 композиций, общие SVG/PDF/PPTX | Композиции не равны сертифицированному Brand Pack |
| Замечание → агент → правка | Ожидание обратной связи, короткие команды, связанный ответ и предложение | Внешний агент должен оставаться активным; закрытый чат MCP сам не запускает |
| Одна сессия Codex | ProjectReviewSession использует один thread для последовательных замечаний | Пока работает локальный worker; восстановления после перезапуска нет |
| Проверить до применения | Визуальное сравнение, названия изменённых полей, ссылка на замечание | Принятие по слайдам целиком; нет merge текстовых диапазонов |
| Таблицы | 2–4 колонки, до 6 строк, источник, редактор ячеек, экспорт | В PPTX текст и фигуры, не Office table |
| Графики | Значения и единицы, типизированная команда set_chart | Ограниченные диаграммы; в PPTX фигуры, не Office chart |
| Изображения | MCP принимает PNG/JPEG, фиксирует SHA-256 и связывает со слайдом | До 600 КБ за вызов; нет image provider и корпоративных политик для него |
| Мобильные правки | Локальный редактор: «Слайды / Обсуждение / Правки» | Нет офлайна и проверки на физических устройствах |
| Облачные инструменты | Брифинг, семантические команды, ответы и чтение обратной связи в HTTP MCP | Sites не зарегистрирован как подключаемый remote MCP; OAuth — отдельная задача |

## Как устроен цикл

~~~mermaid
flowchart TD
  B["Короткий запрос"] --> Q["Вопросы и допущения"]
  Q --> C["Человек подтверждает бриф"]
  C --> S["План аргументации"]
  S --> R["Человек принимает план"]
  R --> D["Композиция слайдов"]
  D --> V["Просмотр и замечание"]
  V --> A["Активная сессия агента"]
  A --> P["Предложение и ответ"]
  P --> H{"Решение человека"}
  H -->|Принять| N["Новая версия"]
  H -->|Доработать| V
  N --> V
~~~

Локальный источник истины — project.json. Материалы хранятся по хешу. Редактор и MCP читают одну папку. Ожидание возвращает замечания в текущий вызвавший агент, а не отправляет сообщение в произвольную вкладку ChatGPT.

Внешний Codex/Claude Code может повторять wait_for_feedback, пока пользователь просит совместную проверку. Второй вариант — локальный review worker: он передаёт замечание одному потоку Codex App Server, проверяет JSON и сохраняет предложение через MCP. Модель не получает права принятия. Интеграционные тесты используют подставной ответ модели; реальная авторизованная генерация в текущем окружении не подтверждена.

Принятие всех изменений связанного предложения закрывает исходное замечание. Частичное принятие и отклонение его не закрывают. Человек также может закрыть замечание вручную. Экран обновляется через polling, а не CRDT.

## Язык для агента

PPTX остаётся форматом передачи. DeckDoc остаётся каноническим документом. Для чтения доступны get_story и get_authoring_guide; для коротких изменений:

~~~json
{"commands":[
  {"op":"set_title","slideId":"slide-7","value":"Пилот проверяет один сценарий"},
  {"op":"set_takeaway","slideId":"slide-7","value":"Объём пилота ограничен и проверяем"}
]}
~~~

Команды компилируются в предложение с before/after. Проверка версии, источников и человеческое принятие сохраняются. Экономия объёма запроса зависит от операции. Benchmark токенов, latency и качества против PPTX/Google Slides не проведён.

## Правила дизайна

Folio: крупная типографика, асимметричная обложка, контрастный вывод, выделенная сторона сравнения. Boardroom: спокойная обложка, светлые поверхности, ровная сетка для управленческих материалов. Classic и Atelier остаются.

Цвета, компания и материалы задаются отдельно от содержания. Рендерер не вставляет обещания или названия Lanka в чужую презентацию. Содержание не меняется при выборе оформления.

Композиции: cover, statement, content, split, steps, metrics, chart, table, image, closing. У каждого рецепта есть назначение и ограничения. Проверки схемы и переполнения необходимы, но не оценивают красоту. Приёмка семейства должна включать короткие и длинные заголовки, русский и английский текст, реальные таблицы/диаграммы/изображения и визуальную проверку PDF.

Следующий слой — полный Brand Pack: палитра, типографика, отступы, рецепты, материалы, правила текста, политики, fixtures и goldens. Только после проверки представителем бренда можно считать его корпоративно сертифицированным. Текущий status в Brand не доказывает прохождение такой процедуры.

## Запуск проекта

~~~bash
npm run build:mcp
npm run start:project -- --root /ABS/CLIENT/PROJECT
codex mcp add lanka-project -- node /ABS/LANKA/.project-runtime/server.mjs --root /ABS/CLIENT/PROJECT
~~~

В сессии агента: получить вопросы, провести брифинг, создать черновик, проверить экспорт. Во время обсуждения повторять wait_for_feedback; изменения отправлять через propose_commands, ответ — через reply_to_feedback.

Для автоматической обработки новых локальных замечаний:

~~~bash
node runtime/project-review.mjs --root /ABS/CLIENT/PROJECT --codex-home /ABS/EMPTY_PRIVATE_RUNTIME
~~~

Нужны установленный runtime Codex из runtime/package-lock.json и OPENAI_API_KEY в окружении. Пустой отдельный runtime исключает наследование конфигурации другого клиента. Не храните ключ в папке презентации. Worker ограничен 20 ответами за запуск, не перехватывает существующий чат и не утверждает изменения. Остановить — Ctrl+C. Это приложение с одним локальным писателем; облачная синхронизация папок не заменяет координацию записи.

## Сверка исследования и кода

Основные сведения о Google подтвердились: [редактируемые деки и уточняющие вопросы](https://workspace.google.com/blog/product-announcements/july-2026-workspace-feature-drop), [Slides MCP](https://developers.google.com/workspace/slides/api/guides/configure-mcp-server), [comments API в Developer Preview 31 августа](https://developers.google.com/workspace/release-notes).

[CreatPPT](https://github.com/seekskyworld/CreatPPT) разделяет семантический документ, рабочее пространство и экспорт. Прочитан установленный код 0.1.4: createSlideElements, refreshSlideElementBindings и измерение строк. Ручные изменения сохраняются через userEdited и scene bindings. Полный перенос его редактора изменил бы нашу каноническую модель и правила review.

Реальное использование стороннего кода перечислено в THIRD_PARTY_NOTICES.md: CreatPPT для intake/геометрии, PptxGenJS для PPTX и другие экспортные библиотеки. Код SeaSlides/PPT Master/Presenton/PPTist/Univer/BlockSuite в этой версии не перенесён. Их возможности нельзя выдавать за наши. «10/10 потенциально» из исследования — не сравнительный тест.

## Что ещё необходимо для промышленного продукта

1. Реальный сквозной запуск с авторизованным агентом клиента, наблюдение ошибок и восстановление прерванной сессии.
2. Один контур пилота: локальный проект либо облачная организация. Workspace/folders, наследование ACL, tenant provisioning, SSO и проверка изоляции.
3. Onboarding Brand Pack, утверждение рецептов, визуальные эталоны и дизайн-проверка с представителем бренда.
4. Поток событий и состояние агента, привязка комментария к тексту/области, проверенная диктовка. Сейчас доступен текстовый комментарий; голосовой pipeline не реализован.
5. Evidence graph, извлечение данных, проверка утверждений и manifest публикации. SourceId и хеш не доказывают истинность цифры.
6. Устойчивые очереди, восстановление jobs, semantic rebase. Не обещать CRDT до реализации.
7. Мобильные, браузерные, нагрузочные и Office-проверки; backup/restore и наблюдаемость перед расширением аудитории.

Сейлз-пример создан реальными локальными stdio MCP-вызовами: вопросы → создание с двумя источниками → lint → PPTX/PDF. Гипотезы аудитории и цели явно сохранены. Это проверка нового пути и оформления, а не доказательство готовности всех пунктов PRD.
