# Перенос файловой библиотеки в PostgreSQL

8 сентября 2026. PLAN-07c/22, личный локальный профиль. Реализованы предварительная проверка, перенос и продолжение работы через HTTP/MCP. Полный корпоративный вход, совместные права, S3 и эксплуатационная приёмка остаются отдельными задачами.

## Что меняется

До переноса редактор объединяет файловые документы/папки с личными документами PostgreSQL. После явного переноса каталог папок и все документы этой библиотеки читаются из PostgreSQL. Существующие серверные презентации и их беседы не копируются и не перезаписываются. Старую файловую презентацию можно подключить к чату как тот же документ, без создания ещё одной копии.

Внутренний ID документа сохраняется. Если прежний ID карточки в библиотеке отличался от него, сервер хранит соответствие: старая ссылка перенаправляется на новый канонический адрес с сохранением query, а старый ID принимается библиотечными HTTP/MCP-операциями. Эти ID резервируются от создания другого документа; импорт и создание используют общую блокировку пространства ID в пределах tenant.

Переносятся текущий DeckDoc/state, бриф, предложения и решения, комментарии/привязки, доступные снимки версий, зарегистрированные материалы, оригиналы и нормализованные изображения, неизменяемые экспорты с паспортами. Исторические файловые SHA-256 доступны как соответствия к каноническим серверным хешам. Старые PDF/PPTX/handoff без паспорта сохраняются как blob с mapping в отчёте; им не приписывается неизвестная версия.

Старые ключи выполненных операций сохраняются отдельно. Повтор подтверждённой правки после переключения возвращает прежний результат. Каталог сохраняет собственные receipts. Повтор самого переноса не создаёт дубликаты и не заменяет уже отредактированный серверный документ исходной копией.

## Проверить и выполнить

Нужны настроенный локальный PostgreSQL-профиль, установленная текущая сборка и приватный config, который уже используется локальным редактором. Утилита не требует запуска модели. Как остальные локальные PG entrypoints, она применяет недостающие миграции схемы при инициализации; `--check` не переносит документы и не переключает каталог.

```bash
npm run build:mcp
node .project-runtime/migrate-library.mjs \
  --config "$PWD/work/agent-chat/config.json" \
  --check --report /tmp/lanka-migration-check.json
```

Отчёт содержит исходный hash, состав и объём, соответствия ID и хешей версий. Содержимое документа и credentials не печатаются в терминал. Подробный report создаётся с правами 0600 и не перезаписывает существующий файл; для следующего отчёта выберите новый путь.

Перед рабочим переключением обновите сервер/MCP, сохраните незавершённый ввод и проверьте восстановление старых вкладок. Завершите активные поручения. Выполнение требует конкретного hash из успешной проверки:

```bash
node .project-runtime/migrate-library.mjs \
  --config "$PWD/work/agent-chat/config.json" \
  --apply --expected-hash HASH_ИЗ_ОТЧЁТА \
  --report /tmp/lanka-migration-applied.json
```

Изменившийся источник, занятый документ, повреждённый материал/снимок, неоднозначный ID, недоступная папка, конфликт receipts или незавершённое серверное поручение останавливают операцию. Отсутствующие исторические данные не выдумываются. Сохраняется только известная текущая версия, если истории ранее не было. Проекты с grants/согласованием отклоняются до отдельного решения о полномочиях; новые разрешения не выдаются миграцией.

## Транзакция и восстановление

Утилита берёт `migration.lock`, затем `library.lock` и `write.lock` документов. Она повторно считывает и проверяет данные под блокировками. Перед записью в БД фиксируется `lanka-migration.json` с исходным hash, идентичностью целевого подключения/владельца и состоянием frozen. Документы, версии, blobs, экспорты, receipts, соответствия и активация каталога фиксируются одной PG-транзакцией.

После переключения прежние `library.lock` и `write.lock` остаются постоянными барьерами. Это также останавливает старые процессы, которые ещё не знают о маркере переноса. Новая файловая реализация прямо сообщает, что библиотека перенесена. Исходные project.json, снимки и материалы не переписываются. Новая версия также блокирует экспорт во время переноса; очень старые процессы могут создавать отдельные экспортные файлы в архиве, поэтому их нужно переподключить. Они не могут сохранить правки канонического project.json через прежний lock-протокол.

Не удаляйте постоянные барьеры для возврата к файловой работе: после новых серверных правок это открыло бы второй изменяемый оригинал. Автоматический обратный перенос не реализован.

Если ошибка произошла после freeze, источник остаётся закрытым. Повтор `--apply` с тем же hash и подключением проверяет сохранённое состояние: повторяет откатившуюся транзакцию либо завершает маркер уже подтверждённого переноса. Новые серверные правки не откатываются. Утилита распознаёт собственные завершённые барьеры, но не удаляет чужие/активные lock-файлы и не объявляет процесс остановленным только по возрасту файла.

Проверены исключения до commit и потеря подтверждения после commit. Внезапный SIGKILL/отключение питания с оставшимся активным migration.lock ещё не принят как автоматическое восстановление: нужен операторский разбор фактического процесса и состояния БД. Нельзя очищать lock-файлы только потому, что повтор долго не отвечает. Это открытый пункт PLAN-25; backup всей установки не заменяется этим переносом.

## Границы

- Поддерживается файловая библиотека `lanka-library/v1` и проекты `lanka-project/v1` с UUID документов. Файловые лимиты — 100 папок/500 документов; общий считываемый объём ограничен 250 МБ. Большие каталоги и нагрузка не приняты. В PG-folder API отдельный лимит пока не установлен; это не обещание неограниченной производительности.
- Фильтры tenant/owner и соответствия проверены в двух инициализированных каталогах. Это не OIDC, RLS, наследование прав или доказательство корпоративной изоляции всех поверхностей. Локальная identity по-прежнему берётся из доверенного config.
- Режим хранения отражается в `lanka_get_capabilities.catalog`: file/mixed/postgres. Гайд объясняет переключение и файловые лимиты. `limits.folders` сохранён как прежнее имя файлового лимита; новые поля — `fileFolders` и `pgFolders`. Папки остаются одноуровневыми; общие проекты и права — PLAN-08/22.
- D1 snapshot import, S3, внешние credential stores и истории внешних Codex-процессов не переносятся этой утилитой. Существующие беседы в PG сохранены; новый чат импортированного документа начинается как отдельная сессия Lanka.

## Проверки и текущая установка

`npm run test:migration` — девять интеграционных проверок с файловым хранилищем, настоящим PostgreSQL, HTTP и stdio MCP. Сравнены state, комментарии, предложения, снимки по старым/новым хешам, исходные/нормализованные JPEG и байты экспортов. Проверены старые ссылки, новая чат-сессия без копии, receipts, корзина/восстановление, два каталога, сохранность существующей PG-беседы, сбои до/после commit, занятый источник, неизвестные зависимости и гонка ID между импортом и созданием.

В текущей рабочей библиотеке выполнен только `--check`: 3 папки, 2 файловых документа, 202 968 байт проверенных данных, статус ready. Рабочий каталог не переключён. Подробный приватный отчёт — `out/library-migration/local-preflight.json`.

Mac заблокирован, поэтому живая приёмка старых вкладок, мобильного экрана и полного сохранения несохранённого ввода при переключении не проведена. Пользовательские вкладки не перезагружались. [Машинный реестр результатов](planning/evidence/library-migration.json) отделяет эту границу от серверных тестов. PLAN-07/08/22/25 и общая цель остаются открытыми в полном объёме.
